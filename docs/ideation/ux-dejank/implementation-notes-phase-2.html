Express alias — kept a one-clause --md-output mention

Context
The spec's alias sketch (clean-tree check, follow ideation, scope guard) contains no generator language, but the contract's criterion 3 checks grep -qi 'md-output' skills/express/SKILL.md — a project-level criterion Phase 1 made pass. No later phase touches the alias's generator wording, so dropping it here would leave the final contract validation failing.
Decision
The alias's intro line lists the artifacts the delegated flow still produces, including "generator-rendered contract.html + contract.md via --md-output". One clause, no section citation, criterion preserved.
Alternative
The literal spec sketch with no md-output mention — rejected because it knowingly regresses a contract success criterion this project is measured against.

Express alias — allowed-tools frontmatter retained

Context
The spec preserves "name, description, argument-hint, disable-model-invocation" and targets under ~30 lines including frontmatter. It is silent on allowed-tools (13 lines of the file), and the 0.18.0 file never had an argument-hint to preserve.
Decision
Kept allowed-tools verbatim. The alias's session executes the whole delegated ideation flow, so dropping the pre-approved tool list would change permission-prompt behavior — and the phase's rollout note promises "behavior is equivalent by construction". The file still lands at 27 lines.
Alternative
Dropping allowed-tools for an even thinner file — rejected: line count is a target, tool pre-approval is behavior.

Routing step — run-mode question placement

Context
Component 1 specifies step 7 as "one AskUserQuestion with tier and route", while the File Changes row describes the absorbed express semantics as a "single tier+run-mode confirmation" (express 0.18.0's Phase 4 shape). Both cannot be literally true in one call: run mode is only meaningful after the express route is chosen, and AskUserQuestion cannot branch mid-call.
Decision
On the plain /ideation path, step 7 asks tier + route (Component 1's explicit design) and the Express finish path asks run mode as its own question. When the alias pre-commits the route, the run-mode question folds into step 7's call in place of the answered routing question — reproducing 0.18.0's one consolidated tier + run-mode confirmation exactly on the path that advertised it.
Alternative
Asking run mode unconditionally as a third question in step 7 — rejected: it is meaningless on the full-review route (5.4's handoff menu owns that choice there) and would present a dead question to most users.

Routing step — "Start over" option absorbed into "Needs changes"

Context
The 0.18.0 approval question offered five options including "Start over — fundamentally off track, re-interview". The spec's key decision enumerates exactly three routing options: express finish, full review, needs changes.
Decision
Followed the spec's enumeration. The re-interview escape survives inside the "Needs changes" handling ("fundamental misunderstanding → back to the interview loop"), so no capability is lost — only the dedicated button.
Alternative
Keeping "Start over" as a fourth routing option — rejected: the spec's option list is explicit, and AskUserQuestion renders an "Other" affordance for freeform answers anyway.
